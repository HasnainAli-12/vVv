# Workflow Taste
- Wants a plan laid out before implementation on non-trivial features ("create a plan first then start working since that's a proper way"; again "plan it out thoroughly" before building a level). Confidence: 0.9
- Expects ambitious, fully fleshed-out results rather than minimal placeholders — explicitly asks the agent not to "just add simple objects" and to build the full course rather than a sketch. Confidence: 0.7
- Delegates creative/design decisions to the agent and explicitly grants autonomy ("do your own setting, use your freedom") rather than wanting to pick options himself. Confidence: 0.8
- Grants that autonomy only within a "nothing breaks" constraint: pairs free-rein creative briefs with an explicit safety caveat ("feel free to use any of those VFX, wherever you want ... just surprise me honestly but in the good way not the wrong way, i dont want anything to break so be careful"). Wants bold, tasteful creative choices, but stability of the working project takes priority over ambition. Confidence: 0.7
- Reports in-game visual/behavioural bugs by the observed symptom, in whichever form is convenient — sometimes a screen recording of Unity play mode (a video file), other times a short plain-language description of what he sees on screen (e.g. "the wall run animation plays for a second, then the character just goes out of animation but still wallruns without the animation"). No fixed preference for one form. Confidence: 0.5
- Bug reports are terse one-liners in casual register ("the climb boosts the player up in the sky bro, doesn't even grab the ledge properly") with no repro steps, logs or values — he tests in play mode and describes what he saw, then expects the agent to locate and fix the root cause on its own rather than ask him to reproduce or gather diagnostics. Confidence: 0.6
- Wants sound assets actually produced ("generate SFX sounds proper ones for jump (grunt sound) and other etc") — an earlier "don't generate" reading was a misread; he wants proper-quality SFX generated, not empty slots or thin stand-ins. Confidence: 0.8
- Improves existing mechanics by handing over external reference material (community articles/tutorials and their pasted example code, e.g. a full third-party controller class he "found online" with "take a look at this code") and expects the agent to read it and fold the applicable techniques into the current custom implementation — not to reintroduce a from-scratch rewrite. Confidence: 0.7
- When a feature still isn't satisfactory, prefers to park it and move on rather than keep iterating: asks for the issue to be written down for a later session ("note it down for now we will do it tomorrow") and immediately switches to the next task. Wants unresolved items captured in a persistent notes/TODO file. Recurring pattern: he manages work as day-scoped batches — hands over a long multi-item "todo list for tomorrow" in one message and expects it written up (e.g. a TODO file) rather than worked immediately. Confidence: 0.7
- Rejects band-aid fixes and demands the root cause be handled: when a mechanic misbehaves, wants the underlying behaviour prevented structurally rather than suppressed by tuning/timing ("please fix this properly"). Repeated symptom reports after a tuned fix are a signal that the approach, not the value, is wrong. Confidence: 0.85
- Prefers to sequence the work himself in steps: after handing over a chunk he expects it completed and verified before he gives the next instruction ("first make sure ... then I'll tell you what to do next"). Confidence: 0.6
- Briefs design work as an exhaustive spec — required elements, explicit scale/constraint rules, strict prohibitions, and a prescribed output format — and expects the deliverable to follow that format and include a self-audit confirming compliance (e.g. a final checklist that every required element appears and nothing prohibited was used). Confidence: 0.7
- When performance or runtime problems persist, expects diagnosis to be grounded in profiler/log measurements and concrete evidence rather than successive speculative tweaks; is willing to provide captured diagnostics and asks the agent to read them. Confidence: 0.9
- When requesting a fix in a project with hand-edited scenes or assets, wants changes tightly scoped to the named issue and existing user edits preserved—avoid rebuilds or unrelated modifications unless explicitly authorized. Confidence: 0.95
- Prefers the agent to make code/asset/inspector changes itself rather than hand back manual steps — when asked to set inspector values by hand, replied "Do it yourself please". Reserves his own effort for what only a human can do (playtesting, verifying in play mode); expects the agent to drive the editor/tooling directly. Confidence: 0.75
- Treats destructive cleanup (deleting unused assets) as high-risk and wants it done carefully and verified rather than as a broad sweep; explicitly fears accidentally removing something still in use ("i don't want anything to break if you accidently delete something we are using, im screwed"). Confidence: 0.8
- When he will supply assets himself, wants a precise drop-in list up front — exact filenames, format and destination folder — so the agent can wire them in one pass once the files land (asked for this for the full SFX set, and again for a non-SFX asset list spanning VFX, UI, animations and models). Wants the list grounded in an actual project scan so it reflects real gaps rather than guesses. When the files do land he keeps the brief equally thin — points at the folder ("21 items in AUDIO / MySFX, wire them all up") and expects the whole set integrated in one pass. Confidence: 0.75
- Uses git as a progress backup: asks to commit and push at natural checkpoints ("now psuh to git", "git commit and push all the work we did today"), and wanted an early initial commit specifically so progress wasn't lost. Confidence: 0.7
- Wants thorough project documentation — a README covering the whole game with every feature spelled out plus the remaining roadmap/TODO list. Confidence: 0.65
- Targets a WebGL browser build and treats a real build as the only meaningful performance benchmark — editor frame time is not accepted as evidence (used profiler/log numbers and an actual build to settle stutter questions). Confidence: 0.6
- Wants deliverables to be concrete and compile-ready: real numeric values rather than vague advice ("give real numbers, not vague advice"), and complete code with no pseudo-code or placeholder comments. Confidence: 0.7
- Wants destructive operations (deleting assets, especially vendor-package internals) gated by a verification/dry-run first — expects the agent to confirm what is actually referenced or used before removing anything, after a "Demo" folder turned out to contain a load-bearing base class. Confidence: 0.85
- Values candor about mistakes and uncertainty over confident-but-wrong claims: responds best when the agent plainly admits an error, flags what is untested/unverified, and stops guessing in favor of measuring. Confidence: 0.75
- Expects the agent to apply the fix itself through tooling rather than hand back a list of manual steps for him to perform ("do it yourself please"). Confidence: 0.7
- Handles git commit/push for him on request, with a descriptive commit message and a check that local and remote are in sync afterwards. Confidence: 0.6
- Wants full end-to-end ownership of a task and explicitly tells the agent never to hand work back to him — "don't ask me to do anything, do it all urself" — including not asking him to make choices, gather diagnostics, or do any setup; he expects to be a passive recipient of a finished result, and states this most plainly when tired and unable to focus. Confidence: 0.75
- Monitors runtime memory footprint as a first-class constraint alongside frame rate and build size — reports high RAM usage as a bug to be reduced ("the project is eating a lot of RAM bro") and expects memory reduction to be treated as part of performance work, not just GPU cost. Confidence: 0.6
- Persists on an unresolved symptom across many fix attempts: re-tests after each change and re-reports the identical symptom rather than accepting the agent's "should be fixed now" — expects continued investigation until the symptom is genuinely gone, not explained away. The re-report is often extremely terse and gives no new detail ("still stuttering, read logs", or a single word like "Still" after a fix that looked complete), and the pattern is domain-independent — it applies to any bug (a death animation, not just performance), not only the ones he complains about at length. Confidence: 0.75
- Judges performance by perceived smoothness, not raw frame rate — keeps reporting "stuttering" even when the profiler shows a high average FPS, so frame pacing (vSync, target frame rate) matters as much as throughput. Confidence: 0.55
- When handing over a tuning/adjustment task, supplies exact numeric values inline (e.g. position/euler/scale triples) and expects the agent to bake them into the relevant component verbatim — locating the right field/prefab itself — rather than asking or proposing alternatives. Confidence: 0.75
- Before using a third-party package's API, expects the agent to detect the installed version first and code against the matching API generation (e.g. Cinemachine 2.x `CinemachineVirtualCamera` vs 3.x `CinemachineCamera`), never mixing generations, and to report which version it found. Confidence: 0.55
- Expects reconnaissance before building: inspect the existing scene hierarchy, the assets actually present, and the real scripts involved, then report what was found and map it against the request. Reuse or extend objects that already exist (e.g. an existing "HUD" GameObject) instead of duplicating them. Confidence: 0.75
- Requires integration against the real existing API: read the components first and never invent method names or events. If a hook is genuinely missing, add the smallest possible change and show it as a diff rather than rewriting or refactoring working scripts. Confidence: 0.75
- Declares areas that are off-limits and expects them left untouched while working on adjacent features (player controller, Animator, character state machine; and the level geometry itself — "do not touch any of the cubes or obstacles or any of the gameobjects" while placing enemies/pickups). Confidence: 0.7
- Wants the analysis/plan surfaced but no confirmation gate before continuing — explicitly asks to be told the layout and then to proceed straight into building ("wait for no confirmation"). Confidence: 0.6
- Gets visibly impatient when the agent stalls mid-task on blockers, confirmations or hand-backs, and pushes for the whole thing to just be finished ("Just complete the HUD bro", "COMEE ONNN COMPLETE THE HUDDD", then all-caps profanity: "MAN FINISH THE FUCKING HUD") — expects the agent to resolve obstacles itself (e.g. import the missing dependency rather than asking him to run a menu item, even when the import blocks the editor bridge) and drive the task end-to-end in one pass instead of returning with a partial state or a "here's where I am" status report. Confidence: 0.75
- For tooling/build deliverables, prefers an editor script with a one-click menu item (e.g. "Tools > Build HUD") that constructs the whole hierarchy over hand-written manual setup steps, and expects the deliverable to close with a concrete test checklist of real in-game actions (take damage, collect orb, rewind, resize window). Confidence: 0.6
- Treats "commit to GitHub" as a cleanup checkpoint, not a raw snapshot: before committing he wants the project folder tidied and unused assets/generated output cleared out ("first we need to clean up the project by removing unused assets / cleaning up project folder"), i.e. repo hygiene is part of the commit task. Confidence: 0.55
